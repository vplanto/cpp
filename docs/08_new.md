## Динамічне виділення пам'яті: `new` та `delete`

Досі ми працювали зі **статичним та автоматичним виділенням пам'яті**: компілятор ще до запуску програми мав знати точний розмір усіх змінних (у стеку — **Stack**), і автоматично звільняв їх при виході з блоку `{}`.

### Чому стека недостатньо?

1. **Фіксований розмір на етапі компіляції:** Розмір масиву на стеку має бути відомий до запуску програми і не може змінюватися під час її роботи. Якщо жорстко задати буфер `int a[500][500];` (`1 МБ`), а фактично потрібна матриця `5x5` — 99.9% пам'яті простоює даремно; якщо ж на вхід прийдуть дані `2000x2000` — вони фізично не влізуть у скомпільований буфер (спроба записати більше елементів спричинить вихід за межі масиву, затирання сусідніх змінних і захисної «канарейки» `Stack Canary` з `stack smashing detected`, як ми розбирали у [Лекції 5](05_functions.md)).
2. **Стек обмежений за розміром (за замовчуванням 1 МБ на Windows, 8 МБ на Linux):** Виділення пам'яті на стеку зводиться до зміщення регістра вершини стека (`RSP`), але спроба оголосити локальний масив `int a[1000][1000];` (`4 МБ`) перевищить ліміт стека на Windows, а `int a[2000][2000];` (`16 МБ`) призведе до аварійного завершення (`Stack Overflow`) і на Linux. Чому ОС не віддає під стек усю доступну оперативну пам'ять?
   * **Багатопотоковість і неперервність адрес:** Стек мусить бути суцільним блоком віртуальних адрес (його не можна розбити на частини чи перемістити без інвалідації вказівників і адрес повернення). Оскільки процес може мати десятки чи сотні потоків виконання (threads) і кожен потребує власного стека, ОС заздалегідь резервує для кожного потоку фіксований адресний діапазон, обмежений сторожовою сторінкою (*guard page*).
   * **Ізоляція помилок рекурсії (Fail-fast) і відмінність від «канарейки»:** На відміну від компіляторної «канарейки» (`Stack Canary` з [Лекції 5](05_functions.md)), яка є 8-байтним числом *усередині кожного стек-фрейму* і перевіряється програмно лише перед `return` для виявлення переповнення буфера, *guard page* — це ціла сторінка віртуальної пам'яті (`4 КБ` без прав читання/запису в MMU) *на самому краю всього стека потоку*. При нескінченній рекурсії або надмірному локальному масиві процесор апаратно перехоплює перше ж звернення до *guard page* (`SIGSEGV` / `STATUS_STACK_OVERFLOW`), не дозволяючи потоку вичерпати фізичну ОЗП системи.
   * **Утримання фізичних сторінок:** `RSP` — це просто вказівник на поточну вершину стека, тому його зсув назад при виході з функції лише змінює межу вільного місця всередині стека, але не повертає вже задіяні фізичні сторінки ОЗП назад операційній системі до завершення потоку (тоді як купа `Heap` дозволяє повертати великі звільнені блоки системі).
3. **Обсяг даних відомий лише під час роботи (Runtime):** Коли користувач запускає браузер, програма не знає наперед, відкриє він 2 вкладки чи 200. Пам'ять потрібно запитувати в операційної системи тоді, коли з'явилася потреба, і повертати одразу, коли вкладку закрили.

Саме ці архітектурні обмеження стека диктують необхідність другої області пам'яті — **"купи" (Heap / Free Store)**. У системному програмуванні це постійний інженерний компроміс (**trade-off**): стек дає мінімальні накладні витрати (одна інструкція зсуву `RSP`) і автоматичне звільнення, але жорстко обмежує розмір і час життя даних межами функції; купа знімає ці обмеження і дозволяє виділяти гігабайти пам'яті в runtime на довільний час, але ціною складнішого пошуку вільних блоків алокатором та повної відповідальності програміста за своєчасне звільнення ресурсів.

Для цього в C++ використовуються оператори `new` та `delete`, які працюють із вказівниками:

  * **`new`**: Запитує блок пам'яті з "купи" (heap) і повертає **адресу** (вказівник) початку цього блоку.
  * **`delete`**: Повертає блок пам'яті, раніше виділений через `new`, назад операційній системі.

```cpp
// Статичне (автоматичне) виділення — пам'ять у стеку (Stack)
int number = 88;
int *p1 = &number; // p1 вказує на комірку в стеку

// Динамічне виділення — пам'ять у купі (Heap)
int *p2 = new int;    // Виділити 4 байти для одного int у купі (там зараз сміття!)
*p2 = 99;             // Записати значення 99 у виділену комірку в купі

cout << "Value: " << *p2 << endl; // Виведе 99

delete p2;            // Звільнити пам'ять у купі. ВАЖЛИВО!
p2 = nullptr;         // Гарна практика: "обнулити" сам вказівник після звільнення
```

### Анатомія рядка `int* p2 = new int(99);` (Stack vs Heap)

Коли ми виконуємо рядок `int* p2 = new int(99);`, пам'ять виділяється **у двох різних місцях одночасно**:

```text
 СТЕК (Stack)                         КУПА (Heap)
+--------------------+               +--------------------+
| int* p2 (8 байтів) | ------------> | Анонімний int      |
| [ 0x55a1b2c0 ]     |               | (4 байти): 99      |
+--------------------+               +--------------------+
 Знищується автоматично               Живе, доки ми явно не
 при виході з блоку {}                викличемо delete p2;
```

  * **Змінна-вказівник `p2`** (8 байтів на 64-бітній системі) лежить **на стеку**.
  * **Саме число `99`** (4 байти) лежить **у купі** і не має власного імені — до нього можна дістатися лише через адресу, записану в `p2`.

### Бліц-питання з практики

1. **Ліва і права частина виразу (LHS vs RHS):** У рядку `p2 = new int;` якого типу значення повертає права частина `new int` — ціле число `int` чи адресу `int*`? І чому зліва у `p2 = new int;` перед `p2` **немає** зірочки `*`, а в наступному рядку `*p2 = 99;` зірочка **є**?
2. **Статична чи динамічна алокація?** Коли ми пишемо просто декларацію `int* p1;` — це статична (стекова) алокація чи динамічна? А чи виділяється пам'ять під параметри у заголовку функції `int sum(const int* begin, const int* end)` до моменту її виклику?
3. **Чому адреса займає саме 4 або 8 байтів?** Чому розмір будь-якого вказівника на 32-бітній ОС становить 4 байти, а на 64-бітній — 8 байтів?

<details markdown="1">
<summary>Натисніть, щоб побачити розбір</summary>

1. **`new int` повертає адресу (`int*`).** Оператор `new` знаходить у купі вільні 4 байти і повертає їхню адресу. Тому у рядку `p2 = new int;` ми записуємо *адресу* безпосередньо у змінну-вказівник `p2` (без `*`). А в рядку `*p2 = 99;` зірочка — це оператор розіменування (`dereference`), який іде за збереженою адресою в купу і кладе туди число `99`. Не плутайте `*` та `&` в оголошенні типу (ліворуч) і у виразах (праворуч)!
2. **Будь-яке оголошення змінної (`int* p1;`) — це автоматична (стекова) алокація** 8 байтів під сам вказівник. Динамічна алокація в купі відбувається лише тоді, коли виконується оператор `new`. Натомість формальні параметри у прототипі функції — це лише опис сигнатури для компілятора; пам'ять на стеку під них виділяється лише під час реального виклику функції (створення Stack Frame).
3. **Адреса пам'яті — це ціле число (номер байта в ОЗП).** У 4 байти (`32` біти) вміщується максимум $2^{32} \approx 4{,}29 \text{ млрд}$ різних адрес — тобто 32-бітна програма фізично не здатна адресувати більше ніж **4 ГБ оперативної пам'яті**. Саме тому сучасні ОС перейшли на 64-бітну адресацію (8 байтів на кожен вказівник).
</details>

### Що лежить у купі одразу після `new`? (Сміття vs Ініціалізація)

Як і для локальних змінних на стеку (`int x;`), у C++ для купи діє принцип нульових накладних витрат (*zero-overhead principle* — програма не витрачає процесорний час на очищення пам'яті, якщо про це явно не попросили). Тому виклик `new int` без ініціалізатора лише резервує 4 байти, але **не заповнює** їх нулями — у комірці залишається випадкове «сміття» з попередніх операцій:

```cpp
// 1. Без ініціалізації — у комірці лежить НЕІНІЦІАЛІЗОВАНЕ СМІТТЯ (garbage)
int *p1 = new int;

// 2. Ініціалізація нулем (value-initialization)
int *p2 = new int();     // *p2 == 0
int *p3 = new int{};     // *p3 == 0 (сучасний стиль C++11)

// 3. Ініціалізація конкретним значенням
int *p4 = new int(88);   // *p4 == 88
double *p5 = new double{1.23};

// 4. Ініціалізація об'єкта класу (виклик конструктора)
Date *date1 = new Date(1999, 1, 1);
```

### Що насправді робить `delete p2;` і навіщо писати `p2 = nullptr;`?

Оператор `delete p2;` **не знищує змінну `p2`** і **не змінює адресу всередині неї**. Він лише повідомляє менеджеру пам'яті ОС: *"Чотири байти в купі за цією адресою більше не зайняті, їх можна віддати іншим"*.

  * Якщо не написати `p2 = nullptr;`, у змінній `p2` залишиться стара адреса — утвориться **висячий вказівник (dangling pointer)**.
  * Повторний виклик `delete p2;` для тієї самої адреси (**double free**) призведе до аварійного падіння програми.
  * Натомість виклик `delete nullptr;` за стандартом C++ є абсолютно безпечним і нічого не робить.

### Питання до групи: час життя стекової змінної vs даних у купі

Порівняймо у функції звичайну локальну змінну на стеку (`x`) та динамічно виділену пам'ять через локальний вказівник (`p1`), для якого забули викликати `delete`:

```cpp
void allocate() {
    int x = 77;            // Локальна змінна на стеку (4 байти)
    int* p1 = new int(88); // Локальний вказівник на стеку (8 байтів) -> число 88 у купі (4 байти)
} // <-- Вихід із функції: що тут відбувається з x, самим p1 та числом 88?
```

Коли виконання доходить до закриваючої дужки `}`, змінна `x` автоматично звільняється зі стека. Чи викличе компілятор так само автоматично `delete` для пам'яті в купі, коли знищуватиме зі стека локальний вказівник `p1`?

<details markdown="1">
<summary>Натисніть, щоб побачити відповідь</summary>

**Ні, автоматичного `delete` не буде!** Це класичний **витік пам'яті (memory leak)**:
* Для стекової змінної `int x = 77;` і ім'я, і самі 4 байти значення лежать у стек-фреймі функції — на закриваючій дужці `}` зсув `RSP` автоматично звільняє і `x` (4 байти), і саму комірку вказівника `p1` (8 байтів).
* Проте компілятор бачить `p1` просто як 8-байтне число (адресу) на стеку і не відстежує, чи володіє воно ресурсом у купі. Тому виділені через `new` 4 байти з числом `88` у **купі (Heap)** нікуди не зникають і залишаються зарезервованими за процесом.
* Оскільки локальний вказівник `p1` зі стека вже знищено (а адресу не повернули через `return`), програма втратила єдиний шлях до цього блоку в купі й більше не зможе звільнити його до завершення роботи. Якщо такий витік трапляється у циклі чи серверному обробнику запитів, процес поступово вичерпає доступну ОЗП.
</details>

## Динамічні масиви: `new[]` та `delete[]`

Динамічно можна виділяти пам'ять і для масивів, розмір яких визначається під час виконання програми (наприклад, вводиться користувачем або зчитується з файлу).

  * **`new T[size]`**: Виділяє неперервний блок пам'яті в купі для масиву з `size` елементів типу `T` і повертає вказівник на його нульовий елемент.
  * **`delete[]`**: **Обов'язково** використовується для звільнення пам'яті, виділеної через `new[]`.

```cpp
int size;
cout << "Enter array size: ";
cin >> size;

// 'size' — це змінна, а не константа часу компіляції.
// У стандарті C++ статичний масив 'int arr[size];' (VLA) заборонений!
// Потрібен динамічний масив у купі:
int *arr = new int[size];     // Елементи містять сміття (garbage)
// int *arr = new int[size]{}; // А з порожніми дужками {} всі елементи обнуляться!

arr[0] = 10;
arr[1] = 20;

delete[] arr; // Звільнення пам'яті ВСІХ елементів масиву
arr = nullptr;
```

**Важливо:**
1. Оператори мають використовуватися строго парами: `new` -> `delete`, а `new[]` -> `delete[]`.
2. Використання `delete` (без `[]`) замість `delete[]` для динамічного масиву призводить до **невизначеної поведінки (Undefined Behavior)**: алокатор не знатиме, що звільняється саме масив, тому пошкодить службові метадані купи, а для масиву складних об'єктів (наприклад, `std::string`) викличе **деструктор** лише для першого елемента (деструктор — це спеціальна функція класу, яка автоматично очищує внутрішні ресурси об'єкта перед його знищенням; детально вивчатиметься в курсі ООП у 2-му семестрі).

## Масиви та вказівники: Глибокий зв'язок

У C++ ім'я масиву в більшості виразів автоматично перетворюється на **вказівник на його перший (нульовий) елемент**.

```cpp
int numbers[] = {10, 20, 30};
// 'numbers' компілятор трактує як '&numbers[0]' (тип int*)
```

Це відкриває можливість **вказівникової арифметики**.

### Вказівникова арифметика та еквівалентність `arr[i]` і `*(arr + i)`

Коли ви додаєте ціле число `i` до вказівника, його адреса збільшується не на `i` байтів, а на **`i * sizeof(type)` байтів** — тобто рівно на `i` елементів вперед!

```cpp
int numbers[] = {11, 22, 33};
int *iPtr = numbers; // iPtr вказує на numbers[0] (нехай адреса 0x1000)

cout << *iPtr << endl;       // 11 (адреса 0x1000)
cout << *(iPtr + 1) << endl; // 22 (адреса 0x1000 + 1 * sizeof(int) = 0x1004)
cout << *(iPtr + 2) << endl; // 33 (адреса 0x1000 + 2 * sizeof(int) = 0x1008)
```

> **Фундаментальне правило C++:** Для компілятора запис з квадратними дужками `arr[i]` є синтаксичним цукром (повним еквівалентом) виразу `*(arr + i)`.
> Це працює **однаково** і для статичних масивів на стеку, і для динамічних масивів у купі:
> - Можна писати `pArray[i] = 42;`
> - Можна писати `*(pArray + i) = 42;`
> Обидва записи скомпілюються в один і той самий машинний код.

### Чим ім'я масиву відрізняється від звичайного вказівника?

Хоча у виразах `numbers[i]` та `*(numbers + i)` ім'я масиву працює як вказівник на перший елемент ([`TestPointerArray.cpp`](https://github.com/vplanto/cpp/blob/main/06-new/TestPointerArray.cpp)), між масивом `int numbers[5]` і окремою змінною-вказівником `int* pNumbers` є дві принципові відмінності:

1. **Ім'я масиву не можна перенаправити на іншу адресу:**
   * Змінна-вказівник `pNumbers` — це окрема 8-байтна комірка в пам'яті, куди можна записати адресу іншого об'єкта (`pNumbers = otherArray;` або зсунути сам вказівник `++pNumbers;`).
   * Ім'я масиву `numbers` не має окремої комірки-вказівника — воно на етапі компіляції жорстко прив'язане до початку буфера на стеку. Спроба змінити цю адресу (`numbers = otherArray;` або `++numbers;`) викличе помилку компіляції.
2. **Оператор `sizeof` повертає розмір усього буфера лише для імені масиву:**
   * Поки ми звертаємося до імені масиву `numbers` у тій самій функції, де його оголошено, компілятор бачить його повний тип `int[5]` і повертає сумарний обсяг буфера в байтах (`5 * 4 = 20`).
   * Для вказівника `pNumbers` тип має вигляд `int*` (кількість елементів у типі відсутня), тому `sizeof(pNumbers)` повертає лише розмір самої 64-бітної адреси (`8` байтів):

```cpp
int numbers[5] = {11, 22, 33, 44, 55};
int* pNumbers = numbers; // pNumbers зберігає адресу numbers[0]

// 1. Перенаправлення:
pNumbers = &numbers[2];  // ДОЗВОЛЕНО: вказівник тепер дивиться на 3-й елемент
// numbers = &numbers[2]; // ПОМИЛКА КОМПІЛЯЦІЇ: ім'я масиву змінити не можна

// 2. Розмір у байтах (sizeof):
cout << sizeof(numbers) << endl;  // 20 байтів (увесь масив: 5 * sizeof(int))
cout << sizeof(pNumbers) << endl; // 8 байтів (розмір самої адреси на 64-бітній ОС)
```

### Передача масивів у функції: втрата розміру ([`TestSizeofArray.cpp`](https://github.com/vplanto/cpp/blob/main/06-new/TestSizeofArray.cpp)) та захист через `const`

Коли масив передається у функцію, він "розпадається" (**array-to-pointer decay**) до звичайного вказівника на свій перший елемент:

  * Жодного копіювання елементів масиву не відбувається — передається лише 8-байтна адреса першого елемента.
  * **Розмір масиву втрачається:** всередині функції `sizeof(arr)` поверне розмір вказівника (`8`), а не масиву. Тому кількість елементів `int size` завжди передають окремим параметром.
  * Сигнатури `void func(int arr[], int size)` та `void func(int* arr, int size)` для компілятора **абсолютно ідентичні**.
  * Оскільки функція отримує прямий доступ до оригінального масиву за адресою, функції, які **тільки читають** масив (пошук максимуму, друк, сума), обов'язково слід захищати ключовим словом **`const`**:

```cpp
// 1. Тільки читання — захищаємо елементи від випадкової зміни через const
int max(const int arr[], int size) {
    // arr[0] = 999; // ПОМИЛКА КОМПІЛЯЦІЇ! Компілятор захистив масив
    int maxVal = arr[0];
    for (int i = 1; i < size; ++i) {
        if (arr[i] > maxVal) maxVal = arr[i];
    }
    return maxVal;
}

// 2. Модифікація — свідомо передаємо без const, щоб змінити оригінал
void replaceByMax(int arr[], int size) {
    int maxVal = max(arr, size);
    for (int i = 0; i < size; ++i) {
        arr[i] = maxVal; // Змінює масив безпосередньо у main()!
    }
}
```

#### Питання до групи

1. Чому у функції `replaceByMax` тип повернення `void` (немає `return`), але після її завершення оригінальний масив `numbers` у `main()` виявляється зміненим?
2. Питання з іспиту: як саме передається сам параметр `int arr[]` (тобто вказівник `int* arr`) у функцію — **за значенням (`by value`)** чи **за посиланням (`by reference`)**?

<details markdown="1">
<summary>Натисніть, щоб побачити відповідь</summary>

1. Тому що масив не копіюється: функція отримує **адресу першого елемента** оригінального масиву з `main()`. Запис `arr[i] = maxVal;` (тобто `*(arr + i) = maxVal;`) розіменовує цю адресу і записує нове значення прямо в комірки пам'яті оригінального масиву.
2. Сам вказівник `arr` (8-байтна адреса) передається **за значенням (`by value`)** — у стеку функції створюється 8-байтна локальна копія цієї адреси. Але оскільки ця копія містить ту саму адресу, що й оригінальний масив у `main()`, будь-яке розіменування `*` або `[]` змінює спільні дані за цією адресою.
</details>

### Робота з діапазоном масиву (`[begin, end)`)

Замість того, щоб передавати `(вказівник + розмір)`, у стандартній бібліотеці C++ прийнято передавати два вказівники: `pBegin` (на перший елемент діапазону) і `pEnd` (на комірку **одразу після** останнього елемента діапазону — напіввідкритий інтервал `[begin, end)`).

```cpp
// Функція, що працює з будь-яким піддіапазоном [pBegin, pEnd)
int sumRange(const int* pBegin, const int* pEnd) {
    int sum = 0;
    for (const int* p = pBegin; p != pEnd; ++p) {
        sum += *p;
    }
    return sum;
}

int main() {
    int arr[] = {10, 20, 30, 40, 50};

    // Сума всього масиву: (arr + 5) вказує на комірку ОДРАЗУ ЗА останнім елементом
    int totalSum = sumRange(arr, arr + 5);       // 10+20+30+40+50 = 150

    // Сума піддіапазону з індексу 1 до 3 включно (індекс 4 не входить):
    int partialSum = sumRange(arr + 1, arr + 4); // 20+30+40 = 90
}
```

## Узагальнені вказівники (`void*`)

Вказівник типу `void*` ([`TestVoidPointer.cpp`](https://github.com/vplanto/cpp/blob/main/06-new/TestVoidPointer.cpp)) — це "сира адреса без типу". Він може зберігати адресу змінної **будь-якого типу** (`int`, `double`, структури тощо).

Проте компілятор не знає, скільки байтів займає об'єкт за адресою `void*`, тому для `void*` **заборонені**:
1. **Пряме розіменування** (`*pVoid` — помилка компіляції, бо невідомо, скільки байтів читати: 1, 4 чи 8).
2. **Вказівникова арифметика** (`pVoid + 1` — помилка компіляції, бо `sizeof(void)` не визначений).

Перед читанням або записом `void*` потрібно явно привести до конкретного типу (наприклад, через `static_cast<int*>(pVoid)`).

> **Примітка:** Синтаксис вказівників на функції та передача операцій як Callback-параметрів ([`TestFunctionPointer.cpp`](https://github.com/vplanto/cpp/blob/main/06-new/TestFunctionPointer.cpp)) розглянуті у [Лекції 6: Вказівники на функції](06_pointers.md#вказівники-на-функції-function-pointers).

## Сучасна практика: Розумні вказівники (Smart Pointers)

Ручне управління пам'яттю за допомогою `new` та `delete` є джерелом багатьох помилок (витоки пам'яті, подвійне звільнення). Сучасний C++ (починаючи з C++11) пропонує краще рішення — **розумні вказівники** з заголовка `<memory>`.

Вони автоматично звільняють пам'ять при виході з блоку `{}` за ідіомою **RAII (Resource Acquisition Is Initialization)** — або в більш точній сучасній інженерній трактовці **SBRM (Scope-Bound Resource Management — керування ресурсами, прив'язане до області видимості)**: час життя ресурсу в купі жорстко прив'язується до часу життя локального об'єкта-обгортки на стеку (детально в курсі ООП у 2-му семестрі).

  * **`std::unique_ptr`**: **Одноосібне (унікальне) володіння.** У конкретний момент часу лише один `unique_ptr` може володіти виділеною коміркою в купі, і пам'ять автоматично звільняється (`delete`), коли він виходить з області видимості `{}`. Копіювати такий вказівник (`u2 = u1`) заборонено компілятором — інакше два власники при виході з `{}` двічі звільнили б ту саму адресу (*double free*). Натомість право володіння можна лише **переміщати** через `u2 = std::move(u1)`: адреса ресурсу переходить до нового власника `u2`, а старий вказівник `u1` автоматично обнуляється в `nullptr`.
  * **`std::shared_ptr`**: **Спільне володіння з підрахунком посилань (`reference counting`).** Дозволяє копіювання: кожна нова копія збільшує внутрішній лічильник власників (`use_count()`), а вихід копії з `{}` зменшує його. Пам'ять у купі звільняється лише тоді, коли знищується *останній* `shared_ptr` (лічильник стає `0`).
  * **`std::weak_ptr`**: **Неволодіючий («слабкий») вказівник-спостерігач** за об'єктом, яким керує `shared_ptr`. Дозволяє перевірити, чи об'єкт ще існує (`lock()`), але не збільшує лічильник власників (використовується для розриву кільцевих посилань у графах та кешах; детально — у 2-му семестрі).

Для створення об'єкта в купі замість ручного `new` використовують фабричні функції `std::make_unique<T>(...)` та `std::make_shared<T>(...)` — це безпечний аналог `new T(...)`, який виділяє пам'ять у купі й одразу загортає отриману адресу в розумний вказівник:

```cpp
#include <iostream>
#include <memory> // Заголовок для std::unique_ptr, std::shared_ptr, std::weak_ptr
using namespace std;

int main() {
    // 1. std::unique_ptr — одноосібний власник
    {
        // make_unique<int>(99) — це прямий аналог new int(99), але без потреби писати delete
        // (те саме, що unique_ptr<int> u1(new int(99));)
        unique_ptr<int> u1 = make_unique<int>(99);
        cout << "u1 value: " << *u1 << endl; // 99

        // unique_ptr<int> u2 = u1;          // ПОМИЛКА КОМПІЛЯЦІЇ: копіювання заборонене!
        unique_ptr<int> u2 = std::move(u1);  // ПЕРЕМІЩЕННЯ володіння: тепер власник — u2, а u1 == nullptr
        cout << "u2 value: " << *u2 << ", u1 is null: " << (u1 == nullptr) << endl;
    } // <-- Тут u2 виходить із блоку {} і автоматично викликає delete (жодних витоків)

    // 2. std::shared_ptr та std::weak_ptr — спільне володіння і спостереження
    {
        // make_shared<int>(42) — аналог new int(42) зі створенням лічильника посилань
        shared_ptr<int> s1 = make_shared<int>(42);
        cout << "Owners count: " << s1.use_count() << endl; // 1 власник

        weak_ptr<int> observer = s1; // Спостерігач: НЕ збільшує лічильник власників (все ще 1)

        {
            shared_ptr<int> s2 = s1; // Копіювання дозволене: спільне володіння тим самим числом 42
            cout << "Owners count inside block: " << s1.use_count() << endl; // 2 власники
        } // <-- s2 знищено, але пам'ять ще НЕ звільнена, бо живий s1

        cout << "Owners count after block: " << s1.use_count() << endl; // Знову 1 власник
    } // <-- Останній власник s1 виходить з {} -> лічильник стає 0 -> пам'ять у купі звільняється

    return 0;
}
```

### Питання до групи

Чому `unique_ptr` вважається "безпечнішим" за сирий вказівник `new`? (Підказка: що станеться, якщо ми виділимо пам'ять через `new`, а потім у функції станеться помилка, і ми вийдемо з неї раніше, ніж дійдемо до `delete`?)

<details markdown="1">
<summary>Натисніть, щоб побачити відповідь</summary>
Якщо ми вийдемо з функції раніше (наприклад, через достроковий `return` або виключення `throw`), наш ручний `delete` ніколи не викличеться, і ми отримаємо **витік пам'яті**. `unique_ptr` — це локальний об'єкт-обгортка на стеку. Навіть якщо ми достроково вийдемо з функції, C++ гарантує, що **деструктор** локального об'єкта `unique_ptr` буде викликаний при виході з `{}`. А цей деструктор автоматично викличе `delete` для пам'яті в купі за нас.
</details>

> **Золоте правило сучасного C++:** Віддавайте перевагу **розумним вказівникам** (`unique_ptr`, `shared_ptr`) та стандартним контейнерам (`std::vector`) над сирими `new`/`delete` для управління динамічною пам'яттю.

## Контрольні питання

1.  **Управління пам'яттю.** Що таке "витік пам'яті" (memory leak)? Де саме в пам'яті (Stack чи Heap) розташовані змінна `p` та число `99` після виконання `int* p = new int(99);`?
2.  **Вказівникова арифметика.** Що виведе наступний код, якщо адреса `arr` дорівнює `0x1000`, а `sizeof(int)` дорівнює 4?
    ```cpp
    int arr[] = {10, 20, 30};
    int* p = arr;
    cout << *(p + 1) << endl;
    cout << (p + 1) << endl;
    ```
3.  **Розпад масиву (Array Decay) та `sizeof`.** Чому для масиву `int a[5]` вираз `sizeof(a)` у `main()` повертає `20`, але всередині функції `void fun(const int arr[], int size)` вираз `sizeof(arr)` повертає `8` (на 64-бітній ОС)?
4.  **Застосування.** Напишіть функцію, яка динамічно створює масив цілих чисел заданого розміру (`size`), заповнює його квадратами чисел від 0 до `size-1` і повертає вказівник на цей масив.

<details markdown="1">
<summary>Натисніть, щоб побачити відповіді</summary>

**1. Витік пам'яті та Stack vs Heap:**

  * Сама змінна-вказівник `p` (8 байтів) розташована на **стеку (Stack)**, а виділені 4 байти з числом `99` — у **купі (Heap)**.
  * **Витік пам'яті (Memory Leak)** виникає, коли вказівник `p` на стеку знищується (при виході з функції) або перезаписується іншою адресою без попереднього виклику `delete p;`. Блок у купі залишається зайнятим, але програма втрачає його адресу.

**2. Вказівникова арифметика:**
Код виведе:

```text
20
0x1004
```

  * **`*(p + 1)`**: `p` вказує на `arr[0]`. `p + 1` — це адреса `p` + `sizeof(int)`, тобто `0x1000 + 4 = 0x1004`. Це адреса другого елемента (`arr[1]`). Оператор `*` розіменовує цю адресу і дістає значення `20`.
  * **`(p + 1)`**: Це просто обчислення адреси другого елемента (`0x1004`).

**3. Розпад масиву (Array Decay) та `sizeof`:**

  * У `main()`, де масив оголошено, компілятор знає його повний тип `int[5]`, тому `sizeof(a)` обчислює розмір усього буфера (`5 * 4 = 20` байтів).
  * При передачі масиву у функцію відбувається *array-to-pointer decay*: параметр `const int arr[]` для компілятора тотожний вказівнику `const int* arr`. Функція отримує лише 8-байтну адресу першого елемента, тому `sizeof(arr)` повертає розмір самого вказівника (`8` байтів на 64-бітній ОС).

**4. Функція створення масиву:**

```cpp
#include <iostream>

// Функція повертає вказівник на int
int* createSquaresArray(int size) {
    // 1. Динамічно виділяємо пам'ять у "купі"
    int* arr = new int[size];

    // 2. Заповнюємо масив
    for (int i = 0; i < size; ++i) {
        arr[i] = i * i;
    }

    // 3. Повертаємо вказівник на початок масиву в купі
    return arr;
}

int main() {
    int n = 5;
    int* myDynamicArray = createSquaresArray(n);

    // Використовуємо масив
    for (int i = 0; i < n; ++i) {
        std::cout << myDynamicArray[i] << " "; // Виведе: 0 1 4 9 16
    }
    std::cout << std::endl;

    // 4. НЕ ЗАБУВАЄМО звільнити пам'ять за допомогою delete[],
    //    коли вона більше не потрібна!
    delete[] myDynamicArray;
    myDynamicArray = nullptr;

    return 0;
}
```

</details>

   - **Перевірка в IDE:** Порівняти еквівалентний запис `*(pArray + i)` та `pArray[i]`; звернути увагу на парність операторів `new[]` та `delete[]`.

3. **[TestPointerArray.cpp](https://github.com/vplanto/cpp/blob/main/06-new/TestPointerArray.cpp)** — *Ім'я масиву як адреса першого елемента та адресна арифметика*
   - **Механізм:** Вирази `&numbers[0]` та `numbers` виводять одну й ту саму адресу, а розіменування `*numbers`, `*(numbers + 1)`, `*(numbers + 4)` напряму звертається до елементів `numbers[0]`, `numbers[1]`, `numbers[4]` через зміщення по `sizeof(int)` байтів.

4. **[TestSizeofArray.cpp](https://github.com/vplanto/cpp/blob/main/06-new/TestSizeofArray.cpp)** — *Розпад масиву до вказівника (Array Decay) при передачі у функцію*
   - **Механізм:** У `main()` вираз `sizeof(numbers)` повертає розмір усього масиву (`20` байтів), а всередині `fun(const int *arr, int size)` вираз `sizeof(arr)` повертає лише розмір вказівника (`8` байтів). Саме тому `size` передається окремим параметром.

5. **[TestArrayPassing.cpp](https://github.com/vplanto/cpp/blob/main/06-new/TestArrayPassing.cpp)** та **[TestArrayPassingPointer.cpp](https://github.com/vplanto/cpp/blob/main/06-new/TestArrayPassingPointer.cpp)** — *Передача масивів у функції та роль `const`*
   - **Механізм:** Заголовки `int max(const int arr[], int size)` та `int max(const int *arr, int size)` для компілятора є ідентичними.
   - **Перевірка в IDE:** Протиставити `max(const int arr[], ...)` / `print(const int arr[], ...)` (де `const` блокує модифікацію елементів на етапі компіляції) та `replaceByMax(int arr[], ...)` (яка змінює масив викликача за адресою). Спробувати дописати `arr[0] = 0;` всередині `print()` і перевірити діагностику компілятора.

6. **[SumArrayRange.cpp](https://github.com/vplanto/cpp/blob/main/06-new/SumArrayRange.cpp)** — *Передача діапазону масиву через два вказівники `[begin, end)`*
   - **Механізм:** Функція `sum(const int *begin, const int *end)` обходить будь-який підмасив (`a` до `a + 10`, `a + 2` до `a + 5`, `&a[2]` до `&a[5]`) без передачі розміру `size`. Це базовий патерн ітераторів стандартної бібліотеки STL (`std::sort(begin, end)`).

7. **[TestVoidPointer.cpp](https://github.com/vplanto/cpp/blob/main/06-new/TestVoidPointer.cpp)** — *Узагальнений вказівник `void*`*
   - **Механізм:** Функція `print(void *p, char type)` приймає адресу змінної довільного типу (`int`, `char`, `double`) і явно приводить її до цільового типу перед розіменуванням.
   - **Перевірка в IDE:** Розкоментувати `*p` або `p + 1` всередині `print()` і перевірити помилку компіляції (компілятор забороняє пряме розіменування та адресну арифметику для `void*`, оскільки невідомий `sizeof` типу).

8. **[TestFunctionPointer.cpp](https://github.com/vplanto/cpp/blob/main/06-new/TestFunctionPointer.cpp)** — *Вказівники на функції та Callback (`arithmetic`)*
   - **Механізм:** Функція `arithmetic(int n1, int n2, int (*operation)(int, int))` приймає адресу функції (`add` або `sub`) як третій аргумент і викликає її всередині себе.
   - **Перевірка в IDE:** Звернути увагу на синтаксичну різницю між `int (*operation)(int, int)` (вказівник на функцію) та `int* operation(int, int)` (прототип функції, що повертає `int*`); додати власну функцію `mul(int a, int b)` і передати її в `arithmetic(number1, number2, mul)` без зміни коду `arithmetic`.

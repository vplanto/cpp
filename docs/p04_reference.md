# Практикум 4: Вказівники та Посилання — Керуємо ігровим світом

## Експрес-опитування

У минулому практикумі ми познайомилися з "небезпечним" інструментом — вказівниками. Давайте переконаємося, що ми пам'ятаємо основи:

1.  Якщо `int score = 9000;`, то що таке `&score`?
2.  Якщо `int* pScore = &score;`, то що таке `*pScore`?
3.  Чому ми повернули `int*` (вказівник), а не `int` (значення) з функції `findBestScorePtr`?
4.  Яке "безпечне" значення ми повертали, якщо функція `findBestScorePtr` нічого не знайшла?

<details markdown="1">
<summary>Натисніть, щоб побачити відповіді</summary>

1.  `&score` — це **адреса** змінної `score` у пам'яті (напр., `0x7ffc...`).
2.  `*pScore` — це **значення**, що лежить за цією адресою (тобто `9000`).
3.  Тому що нам потрібно було **місцезнаходження** (адреса) рекорду, щоб мати змогу його **змінити** (нарахувати бонус).
4.  Ми повертали **`nullptr`**, щоб чітко показати, що валідного результату немає.

</details>

## Розминка: Тренажер сигнатур («Читаємо та дешифруємо контракти функцій»)

Перш ніж писати тіло будь-якої функції, програміст проєктує її **сигнатуру (прототип)**. Сигнатура — це юридичний контракт між тим, хто викликає функцію, і самою функцією.

### Крок 1: Бліц «Прочитай параметр справа наліво»

Пригадаємо головне правило читання типів у C++ — читаємо **справа наліво** (від імені змінної до типу):

| Запис параметра | Як читається справа наліво | Що це означає на практиці |
| :--- | :--- | :--- |
| `int x` | `x` — це змінна типу `int` | **Копія (by value).** Функція працює з клоном, оригінал у безпеці. Для малих чисел. |
| `int& rX` | `rX` — це **посилання (`&`)** на тип `int` | **Псевдонім оригіналу (by reference).** Обов'язково існує, функція **має змінити** оригінал. |
| `const std::string& refText` | `refText` — це **посилання (`&`)** на `string`, який ми **обіцяємо не змінювати (`const`)** | **Тільки подивитись (read-only).** Жодного копіювання мегабайтів тексту + залізний захист від змін. |
| `int* pBonus` | `pBonus` — це **вказівник (`*`)** на тип `int` | **Опціональна адреса (by pointer).** Може вказувати на змінну, а може бути `nullptr` (відсутній). |

#### Задача 1: Алгоритм рекомендацій TikTok / Reels

> 1. *текст опису відео з хештегами `caption` типу `std::string` (може бути дуже довгим, функція його **тільки аналізує і не має права змінювати**);*
> 2. *кількість лайків `likes` типу `int` (просте число, просто читаємо);*
> 3. *рейтинг автора `creatorRating` типу `int` (гарантовано існує; функція **повинна оновити й перезаписати** цей рейтинг після аналізу відео)».*

Якою буде сигнатура функції `analyzeReel`?

<details markdown="1">
<summary>Натисніть, щоб побачити дешифровку</summary>

```cpp
void analyzeReel(const std::string& caption, int likes, int& creatorRating);
```

* **`const std::string& caption`** — читаємо справа наліво: `caption` є посиланням (`&`) на рядок (`std::string`), який обіцяємо не міняти (`const`). Передаємо без копіювання і захищаємо від випадкового псування.
* **`int likes`** — звичайний скалярний тип (4 байти), змінювати оригінал не потрібно, передаємо за значенням (`by value`).
* **`int& creatorRating`** — вихідний параметр (out-parameter). Посилання без `const` дозволяє функції напряму змінити рейтинг автора у коді викликача.

</details>

Якою буде сигнатура функції `startSpotifyJam`?

<details markdown="1">
<summary>Натисніть, щоб побачити дешифровку</summary>

```cpp

```

* **`const std::string& playlistTitle`** — важкий об'єкт тільки для читання → константне посилання.

</details>

#### Задача 3: CS2 / Valorant — вибір кращого скіна для наклейки стікера (Lvalue Return)
> **Запит:** *«Напишіть функцію `selectBestSkin`, яка приймає показники рідкісності двох скінів з інвентарю (`int skinA`, `int skinB` — обидва гарантовано існують у пам'яті) і **повертає пряме посилання на кращий із цих двох скінів**, щоб ми могли у `main()` написати ось такий вираз зліва від `=` (апгрейднути обраний скін на місці):*
> ```cpp
> selectBestSkin(myAwpRarity, dropAwpRarity) += 100;
> ```
> *Якою має бути сигнатура функції `selectBestSkin`?»*

<details markdown="1">
<summary>Натисніть, щоб побачити дешифровку</summary>

```cpp
int& selectBestSkin(int& skinA, int& skinB);
```

* **Параметри `int& skinA, int& skinB`** — обов'язково мають бути передані **за посиланням**! Якби ми передали їх за значенням (`int skinA, int skinB`), функція отримала б локальні копії на стеку, які знищаться при виході з функції, і повернення посилання на них створило б катастрофу (*dangling reference*).
* **Тип повернення `int&`** — функція повертає не числову копію, а **псевдонім** однієї з двох оригінальних змінних із `main()`, тому результат виклику стає повноцінним `lvalue` (дозволяє писати `selectBestSkin(...) += 100;`).

</details>

## Частина 1: Проблема ефективності — "Тільки подивитись"

**Задача:** Уявімо, що нам потрібно написати функцію, яка просто **показує** характеристики гравця (здоров'я, ману, досвід), але не змінює їх.

Спочатку порівняймо два базові підходи — передачу за значенням і передачу за посиланням:

```cpp
// Змінні, що описують нашого гравця
int health = 100;
int mana = 50;
int experience = 12500;

// Спосіб 1: Pass-by-Value (Передача за значенням)
void displayStatsByValue(int h, int m, int e) {
    // Функція отримує КОПІЇ змінних
    std::cout << "HP: " << h << ", MP: " << m << ", EXP: " << e << std::endl;
}

// Спосіб 2: Pass-by-Reference (Передача за посиланням)
void displayStatsByRef(int& h, int& m, int& e) {
    // Функція отримує ПСЕВДОНІМИ оригінальних змінних
    std::cout << "HP: " << h << ", MP: " << m << ", EXP: " << e << std::endl;
}
```

### Питання до групи

Уявіть, що замість `int` ми передаємо величезний масив, що описує інвентар гравця (або великий `std::string` з його біографією). Який з цих двох способів (`ByValue` чи `ByRef`) буде працювати швидше і чому?

<details markdown="1">
<summary>Міркуємо разом...</summary>
`Pass-by-value` змушує комп'ютер щоразу створювати повну **копію** всіх даних. Для великого об'єкта це дуже повільно та неефективно. `Pass-by-reference` не створює копій, а дає прямий "псевдонім" (доступ) до оригіналу, що набагато швидше.
</details>

**Виникає інша проблема:** функція, що приймає посилання, може випадково змінити оригінальні дані!

```cpp
// ... всередині displayStatsByRef ...
h = 0; // Ой! Ми випадково "вбили" гравця, хоча хотіли лише подивитись.
```

**Рішення:** `const` посилання — найкращий друг програміста.

```cpp
// Спосіб 3: Pass-by-const-Reference (Найкращий варіант)
void displayStatsByConstRef(const int& h, const int& m, const int& e) {
    std::cout << "HP: " << h << ", MP: " << m << ", EXP: " << e << std::endl;
    // h = 0; // ПОМИЛКА КОМПІЛЯЦІЇ! Код захищений від випадкових змін.
}
```

> **Висновок 1:** Для передачі "важких" даних, які функція має **тільки читати**, завжди використовуйте **константні посилання (`const &`)**. Це швидко і безпечно.

## Частина 2: Проблема модифікації — "Треба змінити"

**Задача:** Тепер нам потрібна функція для торгівлі, яка **має змінювати** баланс золота двох гравців.

```cpp
int player1Gold = 500;
int player2Gold = 200;
```

### Питання до групи

Спираючись на попередній приклад, який спосіб передачі параметрів нам тут потрібен і чому? (`ByValue`, `ByConstRef` чи звичайний `ByRef`?)

<details markdown="1">
<summary>Міркуємо разом...</summary>
Нам потрібен доступ до **оригінальних** змінних, щоб їх **змінити**.

  * `ByValue` не підходить (змінить копії).
  * `ByConstRef` не підходить (`const` заборонить зміни).
  * Залишається звичайне посилання (`&`). Воно дає доступ до оригіналу і дозволяє зміни.
</details>

Давайте напишемо функцію торгівлі.

```cpp
// Функція приймає посилання і гарантовано змінює оригінали
void trade(int& p1Gold, int& p2Gold, int amount) {
    if (p1Gold >= amount) { // Перевірка, чи є гроші
        p1Gold -= amount;
        p2Gold += amount;
    }
}

// ... у main ...
trade(player1Gold, player2Gold, 100);
// Тепер player1Gold = 400, player2Gold = 300
```

> **Висновок 2:** Для зміни параметрів, які **обов'язково мають існувати**, використовуйте **звичайні посилання (`&`)**.

## Частина 3: Проблема опціональності — "Можливо, змінимо"

**Задача:** Напишемо функцію, що накладає на гравця позитивний ефект ("баф"). Функція збільшує основну характеристику гравця (наприклад, силу), але **опціонально** може збільшити і другорядну (наприклад, витривалість).

### Питання до групи

Як нам передати у функцію другорядну характеристику, якої може і не бути? Чи можемо ми використати посилання (`&`)?

<details markdown="1">
<summary>Міркуємо разом...</summary>
Посилання **не може** бути "порожнім" (`null`). Воно *завжди* має посилатися на існуючу змінну. Отже, для опціонального параметра воно не підходить. Тут нам на допомогу приходять **вказівники**, які ми вивчали минулого разу.
</details>

**Вказівник** — це змінна, яка зберігає **адресу** іншої змінної. Його головна перевага — він може бути `nullptr`, тобто "ні на що не вказувати".

```cpp
void applyBuff(int& mainStat, int* optionalStat) {
    mainStat += 10; // Змінюємо основну характеристику через посилання

    // Перевіряємо, чи нам взагалі передали другорядну характеристику
    if (optionalStat != nullptr) {
        *optionalStat += 5; // Змінюємо її через вказівник (розіменування)
    }
}

int main() {
    int strength = 20;
    int endurance = 15;

    // Випадок 1: Бафаємо обидві характеристики
    // Передаємо 'endurance' за адресою
    applyBuff(strength, &endurance); // strength=30, endurance=20

    // Випадок 2: Бафаємо тільки основну
    // Передаємо 'nullptr' як "порожнє" значення
    applyBuff(strength, nullptr); // strength=40, endurance не змінюється
}
```

> **Висновок 3:** Для зміни параметрів, які можуть бути **відсутніми (опціональними)**, використовуйте **вказівники (`*`)**.

## Частина 4: Критична помилка — "Повернення в нікуди"

**Задача:** Давайте напишемо функцію, яка знаходить, у кого з двох гравців менше здоров'я, і повертає "ручку" (handle), щоб ми могли його вилікувати.

```cpp
// Функція повертає посилання на змінну з меншим значенням
int& findLowerHealth(int& p1Health, int& p2Health) {
    // Повертаємо псевдонім на ОДНУ З ІСНУЮЧИХ змінних
    return (p1Health < p2Health) ? p1Health : p2Health;
}

int main() {
    int p1Health = 50;
    int p2Health = 80;

    // Отримуємо посилання на p1Health і лікуємо його
    findLowerHealth(p1Health, p2Health) = 100;
    // Тепер p1Health = 100
}
```

### Питання до групи

Здається, все працює. А що станеться, якщо ми спробуємо повернути посилання на змінну, створену **всередині** функції?

```cpp
// ДУЖЕ ПОГАНИЙ КОД!
int& createBonus() {
    int bonus = 100; // Це локальна змінна
    return bonus; // Помилка! 'bonus' буде знищено після виходу з функції
}
```

<details markdown="1">
<summary>Міркуємо разом...</summary>

Локальна змінна `bonus` існує лише всередині `createBonus()`. Коли функція завершується, пам'ять, де вона знаходилась (на стеку), звільняється. Посилання, яке ми повернули, стає **"висячим" (dangling reference)** — воно вказує на "сміття".

**Аналогія:** Це як записати адресу готельного номера, з якого ви вже виїхали. Адреса існує, але хто там тепер живе — невідомо.
</details>

> **Висновок 4:** **Ніколи** не повертайте посилання або вказівник на **локальну** змінну.

## Контрольні питання

1.  **Проблема.** Поясніть своїми словами, чому функція `tradeByValue` (якої немає в коді, але уявіть її) не змогла б змінити баланс гравців?
2.  **Посилання.** У вас є функція, яка має **тільки читати** ім'я гравця (уявіть, що це великий об'єкт `std::string`), не змінюючи його. Як ви оголосите її параметр, щоб це було і ефективно, і безпечно?
3.  **Вказівники.** Який оператор використовується, щоб отримати **адресу** змінної? А який — щоб отримати **значення**, що лежить за адресою, збереженою у вказівнику?
4.  **Вибір.** Вам потрібно написати функцію, яка може опціонально застосувати бонус до здоров'я гравця (тобто параметр здоров'я може бути переданий, а може й ні). Що ви оберете для параметра: посилання чи вказівник? Чому?
5.  **Безпека.** Чому код `int& a = createBonus();` (з Частини 4) є небезпечним?

<details markdown="1">
<summary>Натисніть, щоб побачити відповіді</summary>

**1. `tradeByValue`:**
Функція `tradeByValue(int p1Gold, int p2Gold, ...)` отримала б лише **копії** значень `player1Gold` та `player2Gold`. Вона б змінила ці локальні копії, але **оригінальні** змінні у `main()` залишилися б недоторканими.

**2. Ефективне та безпечне читання:**
Потрібно використати **константне посилання**:

```cpp
void printPlayerName(const std::string& name) {
    // ...
}
```

  * `&` (посилання) — для **ефективності** (уникаємо копіювання великого рядка).
  * `const` (константа) — для **безпеки** (гарантує, що функція не змінить оригінал).

**3. Оператори вказівників:**

  * Щоб отримати **адресу**, використовується "амперсанд": **`&`** (напр., `&strength`).
  * Щоб отримати **значення** за адресою, використовується "зірочка" (розіменування): **`*`** (напр., `*optionalStat`).

**4. Опціональний параметр:**
Треба обрати **вказівник (`*`)**.

  * **Причина:** Вказівник може мати спеціальне значення **`nullptr`**, яке чітко сигналізує про "відсутність" параметра. Посилання (`&`) *не може* бути `nullptr`, воно *завжди* має посилатися на реальну, існуючу змінну, тому воно не підходить для опціональних параметрів.

**5. Небезпека `createBonus()`:**

  * Функція повертає посилання на `bonus`.
  * `bonus` — це **локальна змінна**, яка "живе" на стеку функції.
  * Коли функція `createBonus()` завершує роботу, її стек звільняється, і змінна `bonus` **знищується**.
  * Посилання `a` у `main()` стає **"висячим"** — воно вказує на неіснуючу змінну (на "сміття"). Будь-яка спроба використати `a` призведе до невизначеної поведінки.

</details>

### Додаток А: «Детектор брехні» в терміналі — порівняння адрес при Pass-by-Value та Pass-by-Reference

Як на власні очі переконатися, що при передачі за значенням створюється нова змінна у стеку, а при передачі за посиланням функція працює з тією самою коміркою пам'яті? Достатньо вивести адреси (`&`) у `main()` та всередині функції (приклади з репозиторію `05-reference/TestPassByValue.cpp` та `05-reference/TestPassByReference.cpp`):

#### 1. Передача за значенням (`TestPassByValue.cpp`)
```cpp
#include <iostream>
using namespace std;

int square(int n) {
    cout << "In square(): " << &n << endl; // Адреса локальної копії 'n'
    n *= n;
    return n;
}

int main() {
    int number = 8;
    cout << "In main():   " << &number << endl; // Адреса оригіналу 'number'
    cout << "Result:      " << square(number) << endl;
    cout << "After call:  " << number << endl;  // Залишилося 8!
    return 0;
}
```
**Вивід у терміналі (зверніть увагу на останні цифри адреси):**
```text
In main():   0x7ffd8c4e5314
In square(): 0x7ffd8c4e52f4   <-- ІНША АДРЕСА! Це окрема копія у стеку square()
Result:      64
After call:  8
```

#### 2. Передача за посиланням (`TestPassByReference.cpp`)
```cpp
#include <iostream>
using namespace std;

void square(int& rNumber) {
    cout << "In square(): " << &rNumber << endl; // Адреса посилання 'rNumber'
    rNumber *= rNumber;                          // Неявне розіменування (без '*')
}

int main() {
    int number = 8;
    cout << "In main():   " << &number << endl; // Адреса оригіналу 'number'
    square(number);
    cout << "After call:  " << number << endl;  // Стало 64!
    return 0;
}
```
**Вивід у терміналі:**
```text
In main():   0x7ffd3b1a9214
In square(): 0x7ffd3b1a9214   <-- ТІ САМІ БАЙТИ (..214)! Жодної копії не створено
After call:  64
```

### Додаток Б: Інженерна реальність — чому `nullptr` коштує індустрії мільярди доларів?

Навіщо в C++ взагалі ввели посилання (`&`), якщо в мові C вже були вказівники (`*`), якими можна зробити все те саме?

> [!WARNING]
> **Статистика безпеки ПЗ:** За звітами найбільших технологічних компаній (Microsoft, Google, Mozilla), близько **70% усіх критичних вразливостей та аварійних падінь програм** у C/C++ пов'язані з помилками роботи з пам'яттю, серед яких одну з головних ролей відіграє розіменування нульового або неініціалізованого вказівника (`Null Pointer Dereference`).

Уявіть банківський сервер, який обробляє карткові платежі тисяч клієнтів одночасно. Програміст написав функцію проведення транзакції через вказівник `void processPayment(Account* pAcc)` і в одному з десятків розгалужень забув написати перевірку `if (pAcc != nullptr)`. Щойно туди потрапляє порожній вказівник — стається `Segmentation Fault`, і **весь процес платіжного сервера миттєво падає** для всіх користувачів.

Саме тому золоте правило промислового C++ звучить так:
* Якщо об'єкт **обов'язково має існувати** — використовуйте **посилання (`T&` або `const T&`)**. Ви перекладаєте перевірку з людської уважності на **компілятор**: передати `nullptr` у посилання синтаксично неможливо.
* Залишайте **вказівники (`T*`)** виключно там, де відсутність об'єкта (`nullptr`) є частиною бізнес-логіки (як у нашому прикладі з `applyBuff` або `startSpotifyJam`).

### Додаток В: Місток до наступної теми — як законно повернути створене всередині функції значення за адресою? (Стек проти Купи)

У Частині 4 ми побачили, що повертати посилання або вказівник на локальну змінну функції (`createBonus()`) — це катастрофа, оскільки локальні змінні живуть у **стеку (Stack)** і автоматично знищуються при виході з `{}` (`05-reference/TestPassResultLocal.cpp`).

Але що робити, якщо функція дійсно має **створити новий об'єкт з нуля** і повернути його адресу чи посилання так, щоб він **не знищився** після завершення функції?

Саме для цього в C++ існує друга область пам'яті — **купа (Heap)** і оператор динамічного виділення пам'яті **`new`** (`05-reference/TestPassResultNew.cpp`), які ми детально розберемо на наступній лекції:

```cpp
#include <iostream>
using namespace std;

// НЕПРАВИЛЬНО: пам'ять на СТЕКУ (знищується при виході з функції)
int* badCreateOnStack(int value) {
    int localResult = value * value;
    return &localResult; // ПОМИЛКА! Повернення адреси мертвої локальної змінної
}

// ПРАВИЛЬНО: пам'ять у КУПІ (живе, поки ми самі не викличемо delete)
int* goodCreateOnHeap(int value) {
    int* pDynamicResult = new int(value * value); // Виділяємо 4 байти в купі (Heap)
    return pDynamicResult;                        // Безпечно! Дані в купі не зникають при виході з функції
}

int main() {
    int* pSquare = goodCreateOnHeap(8);
    cout << "Значення з купи: " << *pSquare << endl; // Виведе 64 — працює надійно!

    // Оскільки пам'ять у купі не знищується сама, ми ОБОВ'ЯЗКОВО прибираємо за собою:
    delete pSquare;
    pSquare = nullptr;
    return 0;
}
```
